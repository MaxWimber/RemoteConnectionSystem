## D-001: Rust для сервера

Дата: 2026-11-02. Статус: принято.

Решение: серверные компоненты на Rust, тонкая прослойка C++ только для AMF.
Причина: нет сборщика мусора, скорость уровня C++, безопасность памяти в сетевом коде, один исполняемый файл.
Последствия: крейты `windows` и `windows-service`, `unsafe` только в тонких обёртках.

## D-002: TypeScript, Vite и Preact для клиента

Дата: 2026-11-02. Статус: принято.

Решение: один веб-клиент без отдельного мобильного приложения.
Причина: типы, быстрая сборка, маленький размер, знакомый API.
Последствия: критичные обработчики ввода работают вне состояния компонентов.

## D-003: WebRTC как транспорт

Дата: 2026-11-02. Статус: принято.

Решение: видео и ввод передаются через WebRTC, сервер выступает ICE-lite на фиксированном UDP-порту.
Причина: аппаратное декодирование, восстановление потерь и контроль перегрузки уже есть в браузере.
Последствия: WebTransport + WebCodecs остаётся экспериментом после фазы 8.

## D-004: H.264 через AMF

Дата: 2026-11-02. Статус: принято, настройки проверяются в фазе 1.

Решение: H.264, 1080p60, без B-кадров, CBR.
Причина: лучшая поддержка в браузерах и аппаратное кодирование на RX 560. AV1 на карте нет.
Последствия: HEVC рассматривается только в фазе 9.

## D-005: Прямое подключение

Дата: 2026-11-02. Статус: принято. CGNAT устранён белым IP, входящие TCP и UDP проверены, см. `Q-06` и D-013.

Решение: подключение напрямую на белый статический IP, без VPS и TURN.
Причина: минимальная задержка и отсутствие посредника.
Последствия: сети, блокирующие UDP, в первую версию не поддерживаются.

## D-006: Разделение прав процессов

Дата: 2026-11-02. Статус: принято.

Решение: сетевой `rcs-web` работает под ограниченной учётной записью, SYSTEM нужен только `rcs-agent` и `rcs-supervisor`.
Причина: уязвимость в HTTP-слое не должна сразу давать полный контроль над машиной.
Последствия: взаимодействие через именованный канал с ACL.

## D-007: Разработка на сервере

Дата: 2026-11-02. Статус: заменено решением D-009.

Решение: Sonnet 5.5 работает через Claude Code на самом ПК с RX 560.
Причина: захват, AMF и службы Windows проверяются только на целевом железе.
Последствия: рабочий ПК с RTX 3060 не используется для проверки AMF.

## D-008: Только Chrome, Edge и Android Chrome

Дата: 2026-11-02. Статус: принято.

Решение: поддерживаются ПК и Android. Safari и Smart TV вне объёма.
Причина: выбор пользователя, меньше различий API.
Последствия: можно использовать Pointer Lock и Keyboard Lock на ПК.

## D-009: Разработка на рабочем ПК, проверка на сервере по логам

Дата: 2026-11-02. Статус: принято.

Решение: код пишется и собирается на ПК разработки (RTX 3060) в этой же модели, Opus 5.5. Сервер с RX 560 служит
стендом: пользователь запускает на нём готовый пакет и возвращает логи.
Причина: выбор пользователя.
Последствия: на сервере не нужны Rust, Node и Claude Code. Диагностика становится частью продукта. Каждый запуск на
сервере стоит ручного шага, поэтому за один прогон собирается как можно больше данных. Цикл описан в
[TESTING.md](TESTING.md).

## D-010: Бэкенд `mf` с фазы 1

Дата: 2026-11-02. Статус: принято.

Решение: бэкенд Media Foundation реализуется в фазе 1, а не в фазе 8. Бэкенд выбирается настройкой `auto`, `amf`, `mf`.
AMF подключается динамически через `amfrt64.dll`.
Причина: на RTX 3060 нет AMF. Без `mf` весь конвейер нельзя запустить на ПК разработки.
Последствия: один и тот же код собирается на обоих ПК. Замеры с `mf` не считаются подтверждением для AMF.

## D-011: Службы и драйверы только на сервере

Дата: 2026-11-02. Статус: принято.

Решение: на ПК разработки не устанавливаются службы, виртуальные драйверы и правила брандмауэра. Агент здесь запускается
вручную от текущего пользователя, порты слушает только на `127.0.0.1`.
Причина: ПК разработки входит в домен, и внедрение ввода и служб под SYSTEM не должно затрагивать его.
Последствия: фаза 6 и драйвер ViGEmBus проверяются только на сервере. Логика, не требующая их, покрывается
автотестами и подменными реализациями трейтов.

## D-012: Том `D:` остаётся без защиты от отказа диска

Дата: 2026-11-02. Статус: принято.

Решение: том `D:` на 1397 ГБ из трёх дисков не перестраивается.
Причина: выбор пользователя, предпочтение отдано полной ёмкости.
Последствия: отказ любого из трёх дисков приведёт к потере всего тома. Важные файлы нужно хранить ещё и в другом месте.
`files.root` остаётся на `D:\RCS-Storage`.

## D-013: HTTPS на порту 8444

Дата: 2026-11-03. Статус: принято, отменяет порт 443 из D-005 и исходного адреса проекта.

Решение: Caddy слушает HTTPS на TCP 8444, внешний и внутренний порт совпадают. Рабочий адрес:
`https://maxwimber.ru:8444/RemoteConnectionSystem/`. Адрес `http://maxwimber.ru/RemoteConnectionSystem` переадресует на него.
Причина: внешний TCP 443 закрыт, в настройках роутера причины не найдено, пользователь выбрал порт 8444 вместо обращения к провайдеру.
Последствия: `https://maxwimber.ru/` без порта не работает. TCP 80 должен оставаться открытым для переадресации и продления сертификата.
HTTP/3 отключён, потому что UDP 8444 не пробрасывается. `public_origin` и CSP содержат порт.
