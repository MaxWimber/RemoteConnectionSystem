## D-001: Rust для сервера

Дата: 2026-11-02. Статус: принято.

Решение: серверные компоненты на Rust, тонкая прослойка C++ только для AMF.
Причина: нет сборщика мусора, скорость уровня C++, безопасность памяти в сетевом коде, один исполняемый файл.
Последствия: крейты `windows` и `windows-service`, `unsafe` только в тонких обёртках.

## D-002: TypeScript, Vite и Preact для клиента

Дата: 2026-11-02. Статус: принято.

Решение: один веб-клиент без отдельного мобильного приложения.
Причина: типы, быстрая сборка, маленький размер, знакомый API.
Последствия: критичные обработчики ввода работают вне состояния компонентов.

## D-003: WebRTC как транспорт

Дата: 2026-11-02. Статус: принято.

Решение: видео и ввод передаются через WebRTC, сервер выступает ICE-lite на фиксированном UDP-порту.
Причина: аппаратное декодирование, восстановление потерь и контроль перегрузки уже есть в браузере.
Последствия: WebTransport + WebCodecs остаётся экспериментом после фазы 8.

## D-004: H.264 через AMF

Дата: 2026-11-02. Статус: принято, настройки проверяются в фазе 1.

Решение: H.264, 1080p60, без B-кадров, CBR. Управление битрейтом уточнено в D-018: latency constrained VBR.
Причина: лучшая поддержка в браузерах и аппаратное кодирование на RX 560. AV1 на карте нет.
Последствия: HEVC рассматривается только в фазе 9.

## D-005: Прямое подключение

Дата: 2026-11-02. Статус: принято. CGNAT устранён белым IP, входящие TCP и UDP проверены, см. `Q-06` и D-013.

Решение: подключение напрямую на белый статический IP, без VPS и TURN.
Причина: минимальная задержка и отсутствие посредника.
Последствия: сети, блокирующие UDP, в первую версию не поддерживаются.

## D-006: Разделение прав процессов

Дата: 2026-11-02. Статус: принято.

Решение: сетевой `rcs-web` работает под ограниченной учётной записью, SYSTEM нужен только `rcs-agent` и `rcs-supervisor`.
Причина: уязвимость в HTTP-слое не должна сразу давать полный контроль над машиной.
Последствия: взаимодействие через именованный канал с ACL.

## D-007: Разработка на сервере

Дата: 2026-11-02. Статус: заменено решением D-009.

Решение: Sonnet 5.5 работает через Claude Code на самом ПК с RX 560.
Причина: захват, AMF и службы Windows проверяются только на целевом железе.
Последствия: рабочий ПК с RTX 3060 не используется для проверки AMF.

## D-008: Только Chrome, Edge и Android Chrome

Дата: 2026-11-02. Статус: принято.

Решение: поддерживаются ПК и Android. Safari и Smart TV вне объёма.
Причина: выбор пользователя, меньше различий API.
Последствия: можно использовать Pointer Lock и Keyboard Lock на ПК.

## D-009: Разработка на рабочем ПК, проверка на сервере по логам

Дата: 2026-11-02. Статус: заменено решением D-015.

Решение: код пишется и собирается на ПК разработки (RTX 3060) в этой же модели, Opus 5.5. Сервер с RX 560 служит
стендом: пользователь запускает на нём готовый пакет и возвращает логи.
Причина: выбор пользователя.
Последствия: на сервере не нужны Rust, Node и Claude Code. Диагностика становится частью продукта. Каждый запуск на
сервере стоит ручного шага, поэтому за один прогон собирается как можно больше данных. Цикл описан в
[TESTING.md](TESTING.md).

## D-010: Бэкенд `mf` с фазы 1

Дата: 2026-11-02. Статус: принято.

Решение: бэкенд Media Foundation реализуется в фазе 1, а не в фазе 8. Бэкенд выбирается настройкой `auto`, `amf`, `mf`.
AMF подключается динамически через `amfrt64.dll`.
Причина: на RTX 3060 нет AMF. Без `mf` весь конвейер нельзя запустить на ПК разработки.
Последствия: один и тот же код собирается на обоих ПК. Замеры с `mf` не считаются подтверждением для AMF.

## D-011: Службы и драйверы только на сервере

Дата: 2026-11-02. Статус: принято.

Решение: на ПК разработки не устанавливаются службы, виртуальные драйверы и правила брандмауэра. Агент здесь запускается
вручную от текущего пользователя, порты слушает только на `127.0.0.1`.
Причина: ПК разработки входит в домен, и внедрение ввода и служб под SYSTEM не должно затрагивать его.
Последствия: фаза 6 и драйвер ViGEmBus проверяются только на сервере. Логика, не требующая их, покрывается
автотестами и подменными реализациями трейтов.

## D-012: Том `D:` остаётся без защиты от отказа диска

Дата: 2026-11-02. Статус: принято.

Решение: том `D:` на 1397 ГБ из трёх дисков не перестраивается.
Причина: выбор пользователя, предпочтение отдано полной ёмкости.
Последствия: отказ любого из трёх дисков приведёт к потере всего тома. Важные файлы нужно хранить ещё и в другом месте.
`files.root` остаётся на `D:\RCS-Storage`.

## D-013: HTTPS на порту 8444

Дата: 2026-11-03. Статус: принято, отменяет порт 443 из D-005 и исходного адреса проекта.

Решение: Caddy слушает HTTPS на TCP 8444, внешний и внутренний порт совпадают. Рабочий адрес:
`https://maxwimber.ru:8444/RemoteConnectionSystem/`. Адрес `http://maxwimber.ru/RemoteConnectionSystem` переадресует на него.
Причина: внешний TCP 443 закрыт, в настройках роутера причины не найдено, пользователь выбрал порт 8444 вместо обращения к провайдеру.
Последствия: `https://maxwimber.ru/` без порта не работает. TCP 80 должен оставаться открытым для переадресации и продления сертификата.
HTTP/3 отключён, потому что UDP 8444 не пробрасывается. `public_origin` и CSP содержат порт.

## D-014: Сессия Claude Code на сервере для проверок

Дата: 2026-11-04. Статус: заменено решением D-015 до ввода в действие.

Решение: на сервере работает отдельная сессия Claude Code с Remote Control под тем же аккаунтом. Код по-прежнему пишется
и собирается на ПК разработки. Сессия на сервере по заданиям отсюда запускает пакеты, собирает отчёты и проверяет
настройки, а результат возвращает сообщением или файлом.
Причина: каждый ручной прогон стоит поездки к серверу. Прямого доступа нет: сеть ПК разработки не выпускает SSH и порты
сервера кроме 80, а внешний 443 закрыт до сервера.
Последствия: входящие порты не открываются, сервер сам выходит наружу по HTTPS. Действия с правами администратора,
изменения брандмауэра, служб, драйверов и роутера сессия на сервере выполняет только после подтверждения пользователя.
Если сообщения не доходят обратно, результаты передаются файлами, как раньше.

## D-015: Вся работа на сервере

Дата: 2026-11-04. Статус: принято, заменяет D-009 и D-014. D-014 не вводилось в действие.

Решение: проект переносится на сервер с RX 560. Код пишется, собирается и проверяется там одной сессией Claude Code
(Opus 5.5) в приложении Claude. ПК разработки с RTX 3060 больше не используется.
Причина: выбор пользователя. Одно приложение вместо двух, проверка на целевом железе без переноса пакетов и логов.
Последствия: на сервере нужны Git, Rust, Visual Studio Build Tools с C++ и Node.js. Пункты **[ПК]** и **[сервер]** в
`ROADMAP.md` проверяются на одной машине. Бэкенд `mf` (D-010) остаётся запасным путём, но перестаёт быть обязательным
для разработки. Пакеты и `test-phase.ps1` остаются для проверки чистой установки. Службы, драйверы и правила брандмауэра
устанавливаются на этой же машине, поэтому каждое такое действие подтверждает пользователь (D-011 теперь относится к серверу
в этом смысле). Сессия работает от пользователя Windows сервера, права администратора запрашиваются отдельно.

## D-016: Low Latency вместо Ultra Low Latency в AMF

Дата: 2026-11-04. Статус: принято, закрывает Q-01.

Решение: кодировщик AVC работает с `Usage` Low Latency. Ultra Low Latency на текущей среде AMF не используется.
Причина: проба `rcs-bench ull` 4 ноября 2026 года, среда AMF `1.4.31`, драйвер `31.0.21925.1001`. `Init` с Ultra Low
Latency возвращает `AMF_ACCESS_DENIED` даже с одним `Usage`, на 1920×1080, 1280×720 и 640×360, и с любым одним
дополнительным свойством из 16. По трассировке AMF этот режим закрывает свойство `RateControlPreanalysisEnable`
(доступ 0), а `Init` сам читает его в `GetCaps()` и завершается ошибкой `unable to get preencode mode`. Установка
свойства до смены `Usage` и переход с Low Latency на Ultra Low Latency не помогают. Это ошибка среды, а не наших настроек.
Последствия: низкая задержка достигается настройками Low Latency: CBR, малый VBV, `LowLatencyInternal` уже включён.
Значения Ultra Low Latency по умолчанию служат ориентиром для `rcs-bench matrix`: VBV 735 000 бит, `EnforceHRD`
включён, `EncodeLatency` 1000. После обновления драйвера режим перепроверяется командой `rcs-bench ull`.

## D-017: Цвет в VUI дописывает сервер

Дата: 2026-11-04. Статус: принято.

Решение: в SPS каждого IDR от AMF сервер записывает `colour_description`: BT.709 primaries, transfer и matrix,
limited range. Остальные биты SPS копируются без изменений, перезапись проверена тестами на SPS от RX 560.
Причина: AMF `1.4.31` принимает `OutColorProfile`, `OutColorPrimaries` и `OutColorTransferChar`, но пишет в VUI только
`video_full_range_flag`. Без `colour_description` браузер выбирает матрицу сам.
Последствия: работа один раз на IDR, без выделения памяти в установившемся режиме. Если будущий драйвер начнёт писать
цвет сам, перезапись просто заменит те же значения.

## D-018: Latency constrained VBR вместо CBR

Дата: 2026-11-05. Статус: принято, уточняет таблицу начальных настроек AMF в `HARDWARE.md`.

Решение: кодировщик работает в режиме `LATENCY_CONSTRAINED_VBR`, целевой и пиковый битрейт равны. Остальное остаётся
по умолчанию Low Latency: `QualityPreset` Speed, VBAQ выключен, `EnforceHRD` выключен.
Причина: `rcs-bench matrix` 5 ноября 2026 года, AMF `1.4.31`, драйвер `31.0.21925.1001`, 1080p60, 30 Мбит/с, два
ролика по 10 с, и `rcs-bench scenarios` по 60 с на настоящем захвате.
- CBR пропускает кадры до 7,4 целевого размера (204 КБ на видео, 302 КБ на окне при 62,5 КБ на кадр). По сети такой
  кадр идёт несколько интервалов кадра и добавляет столько же к задержке.
- LCVBR держит каждый кадр в пределах 1,0–1,04 целевого: 62,5 КБ на видео и 65 КБ на окне. Средний SSIM тот же
  (0,7664 и 0,9931 против 0,7664 и 0,9933), время кодирования то же, пропусков нет.
- Размер VBV без `EnforceHRD` поток не меняет. CBR с `EnforceHRD` и VBV на 1 кадр даёт 2,0 целевого, `MaxAUSize` на
  2 кадра даёт 1,75.
- VBAQ вместе с CBR ломает управление битрейтом: 122 Мбит/с при цели 30. С LCVBR битрейт в норме, но средний SSIM
  тот же, а PSNR ниже, поэтому VBAQ выключен. Пресеты Balanced и Quality добавляют 1,7 и 10 мс при том же SSIM.
  Usage Webcam и Transcoding медленнее на 4–6 мс.
- Повтор матрицы с LCVBR как baseline (`out/matrix2`) даёт те же выводы: кадр 1,0–1,06 целевого во всех вариантах,
  кроме Constrained Baseline на тексте (1,12).

Последствия: первые кадры после IDR хуже. На текстовом ролике худший кадр SSIM 0,942 и PSNR 25,4 дБ против 0,990 и
35,8 дБ у CBR, затем качество догоняет. IDR остаются редкими: по запросу, после пересоздания и потерь. Если в браузере
это будет заметно, сравниваются `MaxAUSize` на 2 кадра и CBR с `EnforceHRD`.

## D-019: Захват выдерживает частоту потока

Дата: 2026-11-05. Статус: принято.

Решение: цикл захвата берёт новые кадры не чаще частоты потока. Кредит растёт со скоростью потока, но не больше
одного кадра. Кадр берётся, когда кредит не меньше 0,9, и стоит 1. Обновления экрана, которые склеились, пока цикл
выдерживал частоту, считаются сброшенными намеренно, а не пропущенными.
Причина: игра без vsync обновляет экран 230 раз в секунду. Без ограничения `rcs-bench` кодировал каждый пойманный
кадр: 82 к/с и 39,7 Мбит/с при цели 60 к/с и 30 Мбит/с. Простой порог «не раньше 0,9 интервала» давал 65 к/с.
Последствия: с кредитом игра без vsync даёт 59,94–59,99 к/с и 29,0 Мбит/с. Источник с частотой дисплея не ждёт:
окно и видео идут 60 к/с, ни одного кадра не сброшено намеренно. Агент в фазе 2 переносит это правило.

## D-020: WebRTC на `str0m` с криптографией Windows

Дата: 2026-11-05. Статус: принято, закрывает выбор библиотеки в Q-03.

Решение: `rcs-webrtc` построен на `str0m` `=0.25.0` без функций по умолчанию, с `wincrypto`: DTLS и SRTP идут через
CNG и SChannel Windows. Версия закреплена точно, обновление только отдельным решением.
Причина: проверка 5 ноября 2026 года. Обе библиотеки живые: `str0m` 0.25.0 вышел 3 ноября, `webrtc-rs` 0.21.1 —
11 октября. `str0m` устроен как sans-IO: UDP-сокет, время и потоки держит приложение, поэтому сетевая работа не
попадает в потоки захвата и кодирования. В нём есть ICE-lite с отдельным тестом, H.264, запросы ключевого кадра (PLI,
FIR), NACK, каналы данных и расширение `playout-delay` в API отправки (Q-04). С `wincrypto` сборка на сервере прошла
за 50 с без OpenSSL, CMake и NASM.
Последствия: `Writer::write` копирует кадр в `Arc<[u8]>`, это одно выделение памяти на кадр в сетевом потоке, а не в
захвате или кодировании. Задержка библиотеки проверяется замером в P2-7, после него Q-03 закрывается полностью.
Запасной вариант `webrtc-rs` остаётся.

## D-021: Вход в `rcs-web`: библиотеки и хранение

Дата: 2026-11-05. Статус: принято.

Решение:

- Пароль: Argon2id из крейта `argon2` 0.5 (RustCrypto), `m=19456`, `t=2`, `p=1`, хэш в формате PHC. TOTP по
  RFC 6238 написан в `rcs-web` на `hmac` и `sha1` и проверяется на векторах из RFC. SHA-256 из `sha2` для токенов
  сессий и кодов восстановления, случайные данные из `getrandom` (системный генератор Windows). Секрет TOTP шифруется
  DPAPI в контексте машины через `windows`. QR-код для приложения TOTP выводится в консоль крейтом `qrcode`.
- Секреты лежат в одном файле `%ProgramData%\RCS\secrets\auth.json`: хэш пароля, зашифрованный секрет TOTP, хэши кодов
  восстановления и номер последнего принятого шага TOTP. Файл перезаписывается целиком через временный файл.
- Коды восстановления: 8 случайных кодов по 80 бит, хранятся как SHA-256. Перебор по такому хэшу не проще перебора
  самого кода, поэтому Argon2 для них не нужен.
- Сессии и счётчики попыток хранятся в памяти: перезапуск `rcs-web` требует нового входа. Последний принятый шаг TOTP
  хранится на диске, чтобы перезапуск не позволил повторить код.
- Предварительная и полная сессии используют одну cookie `__Secure-rcs_session`. После TOTP выдаётся новый токен.
- Caddy не удаляет префикс `/RemoteConnectionSystem`: `rcs-web` сам обслуживает адреса с ним, как в фазе 2.
- HSTS выставляет Caddy. Остальные заголовки из `SECURITY.md` выставляет `rcs-web`, чтобы они были и без Caddy.
- До фазы 6 нет службы `rcs-web` и учётной записи `NT SERVICE\rcs-web`. `rcs-web` работает от учётной записи
  пользователя, и в ACL каталога секретов вместо `NT SERVICE\rcs-web` стоит она. В фазе 6 её заменяет учётная запись
  службы, как и у канала агента.

Причина: крейты RustCrypto широко используются и не тянут C-код. TOTP занимает несколько десятков строк, отдельная
библиотека для него не нужна. Одна сессия и один пользователь не требуют базы данных.
Последствия: в отладочной сборке `argon2` и `blake2` собираются с оптимизацией, иначе тесты входа идут секундами.

## D-022: Ввод в фазе 4: включение, проверка и курсор

Дата: 2026-11-06. Статус: принято.

Решение:

- Эмуляцию ввода в Windows включает флаг агента `--input sendinput`. Без него агент принимает, проверяет и считает
  события, но в Windows их не передаёт (`--input record`, по умолчанию). Автотесты не вызывают `SendInput` и
  `InjectTouchInput`: они проверяют перевод событий в структуры `INPUT` и `POINTER_TOUCH_INFO` и учёт нажатого.
- Каналы `input-fast` и `input-reliable` разбирает сетевой поток `rcs-webrtc` и без ожидания передаёт события
  потоку ввода агента через очередь на 1024 события. Поток ввода работает с приоритетом выше обычного и владеет
  `InputSink`. Если очередь переполнена, событие отбрасывается и учитывается, а поток ввода затем отпускает всё
  нажатое, чтобы потерянное отпускание не оставило залипшую клавишу.
- Абсолютные координаты `0..65535` относятся к захватываемому монитору: агент переводит их в его прямоугольник на
  рабочем столе и передаёт `SendInput` с `MOUSEEVENTF_ABSOLUTE | MOUSEEVENTF_VIRTUALDESK`.
- Общие примеры сообщений лежат в `crates/rcs-protocol/vectors/input.json` (байты в hex и поля). Их читают тесты Rust
  и TypeScript.
- Фаззинг разбора: `cargo fuzz` требует nightly, на сервере только stable. Поэтому разбор проверяется в `cargo test`
  детерминированным перебором: случайные байты всех длин, мутации общих примеров, обрезанные и удлинённые сообщения.
  Разбор не паникует, а каждое принятое сообщение кодируется обратно в те же байты.
- Курсор: Desktop Duplication не рисует его в кадре. Форму поток захвата берёт `GetFramePointerShape` только при её
  смене и передаёт потоку ввода. Поток ввода переводит её в RGBA и сжимает в PNG крейтом `png` (чистый Rust) для
  `CursorShape`. Положение из `PointerPosition` уходит в `CursorState`. Клиент рисует курсор сам: в обычном режиме
  через CSS `cursor`, при Pointer Lock поверх видео.
- Задержка ввода меряется в часах клиента без синхронизации: тестовая страница на сервере меняет цвет квадрата по
  нажатию, клиент в режиме замера отправляет нажатие и ищет смену цвета в показанных кадрах
  (`requestVideoFrameCallback` и `canvas`).

Причина: сервер является рабочим компьютером пользователя, и `SendInput` действует на активное окно. Тестовое окно
это не изолирует, поэтому настоящий ввод идёт только тогда, когда пользователь управляет компьютером сам.
Последствия: ручные проверки Gate идут с флагом `--input sendinput`, агент с этим флагом запускается по
подтверждению пользователя. Окна с повышенными правами и безопасный рабочий стол недоступны до фазы 6 (UIPI).

Дополнение 2026-11-06, после первой ручной проверки: тачпад на телефоне шлёт абсолютные движения с собственным
ускорением, а не относительные: ускорение указателя Windows делало мелкие введённые сдвиги почти незаметными. На ПК
курсор над видео виден всегда: Windows прячет свой указатель после касаний и не возвращает его на введённую мышь.

Дополнение 2026-11-06, решение пользователя: режим тачпада на телефоне убран, остаётся только прямое касание через
`InjectTouchInput` и экранная клавиатура. Тачпад пользователь счёл бесполезным, а прямое касание работает хорошо.
Правый щелчок и прокрутка с телефона выполняются жестами самой Windows: удержание пальца и два пальца.

## D-024: Геймпады: ViGEmBus 1.22.0 и `vigem-client`

Дата: 2026-11-06. Статус: принято, драйвер установлен 2026-11-06 по подтверждению пользователя.

Решение:

- Виртуальный контроллер Xbox 360 через драйвер ViGEmBus 1.22.0, последний выпуск. Установщик берётся только из
  выпуска на GitHub (`nefarius/ViGEmBus`), перед запуском проверяются подпись Authenticode и SHA-256.
  Устанавливает пользователь через `deploy/install-vigembus.ps1` с UAC.
- Связь с драйвером: крейт `vigem-client` 0.1.4 (MIT, чистый Rust поверх `DeviceIoControl`), без C++ и без
  `ViGEmClient.dll`. Крейт тянет `winapi` 0.3, на остальной код это не влияет.
- `GamepadBackend` живёт в потоке ввода агента рядом с `InputSink`. Контроллер подключается к шине при первом
  состоянии этого номера и отключается при закрытии медиасессии. Тишина 500 мс обнуляет его, не отключая.
  Отпускание всего (обрыв, потеря фокуса, `ReleaseAll`) тоже обнуляет все геймпады.
- Без драйвера агент работает дальше: геймпады только считаются, причина видна в статусе и в клиенте (P5-2). С
  `--input record` геймпады тоже только записываются.

Причина: ViGEmBus остаётся единственным широко используемым способом создать контроллер XInput из обычного процесса;
проект закрыт автором в 2023 году, но подписанный драйвер работает на Windows 10 и 11 (проверка — Q-09). Чистый
Rust сохраняет инвариант о C++ только в `native/amf_shim`.
Последствия: обновлений драйвера не будет. Если на этой сборке Windows он не заработает, запасной вариант из Q-09 —
режим без виртуального геймпада.

## D-025: Службы фазы 6: устройство, установка и откат

Дата: 2026-11-06. Статус: принято, установка служб ждёт подтверждения пользователя.

Решение:

- Службы пишутся на крейте `windows-service` 0.8 (Mullvad, MIT/Apache-2.0): диспетчер, обработчик команд,
  `SERVICE_CONTROL_SESSIONCHANGE`. Остальное — через `windows`.
- Файлы программы ставятся в `C:\Program Files\RCS` (`rcs-supervisor.exe`, `rcs-agent.exe`, `rcs-web.exe`, `web\`),
  данные остаются в `%ProgramData%\RCS` (`secrets`, `logs`, `Caddyfile`). Правило брандмауэра 8443/UDP
  переводится на установленный `rcs-agent.exe`.
- `rcs-supervisor` — служба под SYSTEM в сессии 0, сети не слушает. Параметры агента записаны в командной строке
  службы после `--`. Супервизор берёт активную консольную сессию (`WTSGetActiveConsoleSessionId`), дублирует свой
  токен, ставит `TokenSessionId` и запускает агента `CreateProcessAsUserW` на `winsta0\default`. Агент сам
  переключает потоки захвата и ввода на текущий входной рабочий стол (`OpenInputDesktop`, `SetThreadDesktop`).
- Перезапуск агента: пауза 1, 2, 4, … до 30 с, сбрасывается после минуты работы. Смена консольной сессии
  перезапускает агента в новой.
- Остановка: супервизор взводит именованное событие, агент отпускает весь ввод, отключает геймпады и выходит;
  через 5 с без выхода процесс завершается принудительно.
- Ctrl+Alt+Del: агент передаёт запрос супервизору по каналу `\\.\pipe\rcs-supervisor` (DACL: только SYSTEM),
  супервизор вызывает `SendSAS`. Нужна политика `SoftwareSASGeneration`, её меняют только по подтверждению
  пользователя (P6-7).
- `rcs-web` — служба под виртуальной учётной записью `NT SERVICE\rcs-web` (`rcs-web service`). В ACL каталога
  секретов, `audit.log` и канала агента пользователь заменяется на неё (D-021). Права администратора у неё нет.
- Журнал событий Windows: источник `RCS Supervisor` в журнале «Приложение» для запуска, остановки, перезапусков и
  ошибок; подробные журналы JSON в `%ProgramData%\RCS\logs`.
- `deploy/install.ps1` ставит и обновляет всё повторяемо; `-Uninstall` удаляет службы, правила и файлы программы,
  сохраняя секреты и журналы, и возвращает ручной запуск фаз 3–5. Откат проверяется до проверок Gate.
- Для разработки `rcs-supervisor run --as-user` запускает агента от текущего пользователя без службы: так
  перезапуск и остановка проверяются без прав администратора.

Дополнение 2026-11-07, решение пользователя: из пункта Gate фазы 6 «Работают блокировка, запрос UAC, выход, смена
пользователя, сон монитора» исключаются смена пользователя (второй учётной записи на сервере нет) и сон монитора
(пользователь его не включает). Остальное в пункте проверяется как прежде.

Причина: так устроено в `ARCHITECTURE.md`; `windows-service` — самый распространённый крейт для служб Windows,
писать диспетчер вручную нет смысла.
Последствия: установка, смена политики и перезагрузки выполняются только с подтверждения пользователя.

## Обзоры безопасности

### 2026-11-06: фаза 3, вход и публикация через Caddy

Просмотрены `rcs-web` (вход, сессии, ограничение попыток, сигналинг, журнал, секреты), клиент входа, `Caddyfile`,
скрипты развёртывания. Проверки на сервере в заметках фазы 3 в `ROADMAP.md`, отчёты в `out/phase-03`.

Найдено и исправлено:

- Параллельные попытки обходили ограничение: блокировка проверялась до проверки пароля или кода, а ошибка
  засчитывалась после. Из 20 одновременных кодов TOTP с одного адреса проверялись все 20. Теперь проверка
  блокировки, сама проверка и учёт ошибки идут под одной блокировкой, по одной попытке за раз; тест
  `parallel_guesses_do_not_slip_past_the_limit` падает на прежнем коде.
- `audit.log`, созданный командой от администратора, был недоступен `rcs-web`. Команды теперь не создают журнал.
- Поле кода восстановления наследовало `maxlength=0` от поля TOTP (функциональная ошибка, вход по коду был невозможен).

Проверено без замечаний:

- Защита `/api` закрыта по умолчанию: любой путь, кроме пяти адресов входа, требует полной сессии, включая
  неизвестные пути и пути с лишней косой чертой. `Origin` сравнивается целиком, `X-RCS-Request` обязателен для
  изменяющих запросов, WebSocket без `Origin` отклоняется.
- Cookie `__Secure-` с `Secure`, `HttpOnly`, `SameSite=Strict`; токен 256 бит, на сервере только SHA-256; токен
  меняется после TOTP; новый вход завершает прежние сессии; выход и истечение закрывают WebSocket и сеанс агента.
- Argon2id делает одинаковую работу при любом пароле, ответы для пароля и кода одинаковые. Повтор TOTP запрещён и
  после перезапуска. Коды восстановления сравниваются с постоянным временем и гасятся.
- `X-Forwarded-For` учитывается только от `127.0.0.1`; Caddy не передаёт подделанный клиентом заголовок (проверено:
  в журнале записан настоящий адрес).
- Секретов нет в репозитории и журналах; Caddy заменяет `Cookie` и `Set-Cookie` на `REDACTED`.
- Заголовки из `SECURITY.md` приходят по одному разу, CSP без встроенных скриптов. `rcs-web` слушает только
  loopback и не запускается без секретов.
- `cargo audit` 0.22.2: 153 зависимости, база RustSec на 2026-11-06 (1409 записей), находок нет. `npm audit`: 0
  после обновления `vitest` до 5.1.
- 8443/UDP: агент отвечает только сеансу, открытому `rcs-web` после входа: ICE-проверки требуют `ufrag` и пароль из
  SDP, отпечаток DTLS передаётся через авторизованный WSS. Остальные пакеты отбрасываются.

Принятые риски:

- До фазы 6 `rcs-web` работает от учётной записи пользователя (D-021).
- Общая блокировка после 20 ошибок за час закрывает вход и владельцу на 15 минут. Это цена защиты от перебора
  с многих адресов, как требует `SECURITY.md`.
- Попытки проверяются по одной: поток неверных паролей с разных адресов замедляет вход владельца до срабатывания
  общей блокировки, одна проверка Argon2 занимает десятки миллисекунд.
- `audit.log` читают локальные пользователи компьютера: в нём адреса и события, секретов нет.
- Сессии хранятся в памяти: перезапуск `rcs-web` требует нового входа.
