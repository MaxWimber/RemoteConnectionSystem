# Протокол

Текущая версия: `1`. Числа в бинарных сообщениях little-endian. Источник истины: крейт `rcs-protocol`.
Тесты с общими бинарными примерами обязательны для Rust и TypeScript.

Все пути ниже указаны относительно `/RemoteConnectionSystem`. Caddy передаёт их `rcs-web` вместе с префиксом (D-021).

## Авторизация

Защита запросов: cookie из [SECURITY.md](SECURITY.md), проверка `Origin` и заголовок `X-RCS-Request: 1`
для запросов, меняющих состояние.

| Метод и путь | Тело | Ответ |
|---|---|---|
| `POST /api/auth/login` | `{ "password": "..." }` | `200`, cookie предварительной сессии, `{ "next": "totp" }` |
| `POST /api/auth/totp` | `{ "code": "123456" }` | `200`, cookie сессии |
| `POST /api/auth/recovery` | `{ "code": "..." }` | `200`, cookie сессии, код погашается |
| `POST /api/auth/logout` | Нет | `204` |
| `GET /api/auth/me` | Нет | `{ "authenticated": true, "expires_at": "..." }` или `401`, после пароля с `"next": "totp"` |

Ошибки имеют вид `{ "error": "code" }`. Для неверного пароля и кода используется общий код `invalid_credentials`.
Без сессии любой другой `/api/*` отвечает `401` и `unauthorized`, при чужом `Origin` или без `X-RCS-Request` — `403` и
`forbidden`.
При ограничении попыток: `429` и заголовок `Retry-After`.

## Сигналинг

`GET /api/signal`: WebSocket, только с действующей сессией. Сообщения JSON.

| Направление | Сообщение |
|---|---|
| Клиент → сервер | `{ "v": 1, "type": "offer", "sdp": "..." }` |
| Сервер → клиент | `{ "v": 1, "type": "answer", "sdp": "..." }` |
| Клиент → сервер | `{ "v": 1, "type": "restart" }` |
| Сервер → клиент | `{ "v": 1, "type": "session-replaced" }` |
| Сервер → клиент | `{ "v": 1, "type": "error", "code": "..." }` |
| Оба | `{ "v": 1, "type": "ping", "id": 1 }` и `{ "v": 1, "type": "pong", "id": 1 }` |

Порядок установки:

1. Клиент создаёт `RTCPeerConnection`, видеотрансивер `recvonly` и каналы данных.
2. Клиент отправляет `offer` после завершения сбора кандидатов или сразу без них.
3. Сервер отвечает `answer` с кандидатами: публичным `public_ip:8443` и локальным адресом сервера.
4. Сервер является ICE-lite, STUN и TURN не используются.

При несовпадении версии отправляется `error` с кодом `protocol_mismatch`.

Когда сессия входа заканчивается (выход, истечение, новый вход), сервер отправляет `error` с кодом `session_ended` и
закрывает WebSocket с кодом `4401`. Клиент не переподключается, а показывает страницу входа. Сеанс агента закрывается
сразу. Открытый поток продлевает простой сессии.

После 15 с тишины сервер отправляет кадр WebSocket `Ping`, браузер отвечает `Pong` сам. Сокет, от которого 45 с не
пришло ни одного кадра, сервер закрывает как оборванный и завершает сеанс агента.

## Каналы данных

| Метка | Настройки | Назначение |
|---|---|---|
| `input-fast` | `ordered: false`, `maxRetransmits: 0` | Мышь, геймпад, положение курсора |
| `input-reliable` | `ordered: true` | Клавиши, кнопки, колёсико, касания, текст |
| `control` | `ordered: true` | Настройки, статистика, форма курсора |

Первый байт бинарного сообщения равен его типу. Неизвестный тип игнорируется и учитывается в счётчике.
Сообщение неправильной длины отбрасывается. Строковые кадры в `control` содержат JSON.

Сообщение с полем вне допустимых значений тоже отбрасывается: булевы поля только `0` или `1`, в `flags` у `Key`
занят только бит 0, `pad` от 0 до 3, кнопка от 0 до 4, `phase` от 0 до 3, в `Touch` от 1 до 10 записей, `Text` в
UTF-8. Общие примеры правильных и неправильных сообщений: `crates/rcs-protocol/vectors/input.json`.

### `seq`

`seq` типа `u16` ведётся отдельно для каждого типа сообщений. Сравнение выполняется с учётом переполнения
по правилам RFC 1982. Сообщение со старым `seq` отбрасывается.

### `input-fast`: клиент → сервер

**`0x01` MouseMoveAbsolute, 7 байт**

| Смещение | Тип | Поле |
|---|---|---|
| 0 | `u8` | Тип |
| 1 | `u16` | `seq` |
| 3 | `u16` | `x`, 0..65535 |
| 5 | `u16` | `y`, 0..65535 |

Координаты нормированы по области видео.

**`0x02` MouseMoveRelative, 11 байт**

| Смещение | Тип | Поле |
|---|---|---|
| 0 | `u8` | Тип |
| 1 | `u16` | `seq` |
| 3 | `i32` | Сумма `dx` с начала сессии |
| 7 | `i32` | Сумма `dy` с начала сессии |

Передаётся накопленная сумма, поэтому потеря пакета не теряет движение: сервер применяет разницу с последним значением.

**`0x03` GamepadState, 16 байт**

| Смещение | Тип | Поле |
|---|---|---|
| 0 | `u8` | Тип |
| 1 | `u16` | `seq` |
| 3 | `u8` | `pad`, 0..3 |
| 4 | `u16` | `buttons`, биты как в `XINPUT_GAMEPAD` |
| 6 | `u8` | `left_trigger` |
| 7 | `u8` | `right_trigger` |
| 8 | `i16` | `left_x` |
| 10 | `i16` | `left_y` |
| 12 | `i16` | `right_x` |
| 14 | `i16` | `right_y` |

Состояние передаётся целиком при изменении и не реже чем раз в 50 мс. Через 500 мс тишины сервер обнуляет геймпад.
Для `seq` у каждого `pad` отдельный счётчик.

### `input-fast`: сервер → клиент

**`0x21` CursorState, 8 байт**

| Смещение | Тип | Поле |
|---|---|---|
| 0 | `u8` | Тип |
| 1 | `u16` | `seq` |
| 3 | `u8` | `visible` |
| 4 | `u16` | `x`, 0..65535 |
| 6 | `u16` | `y`, 0..65535 |

### `input-reliable`: клиент → сервер

| Тип | Размер | Формат |
|---|---|---|
| `0x10` Key | 4 | `u8 type`, `u8 flags`, `u16 scancode` |
| `0x11` MouseButton | 3 | `u8 type`, `u8 button`, `u8 down` |
| `0x12` Wheel | 5 | `u8 type`, `i16 dx`, `i16 dy` |
| `0x13` Touch | Переменный | `u8 type`, `u8 count`, затем `count` записей |
| `0x14` ReleaseAll | 1 | `u8 type` |
| `0x15` Text | Переменный | `u8 type`, `u16 length`, UTF-8 |
| `0x16` Special | 2 | `u8 type`, `u8 code` |

- `Key`: бит 0 в `flags` означает нажатие. `scancode` использует набор PS/2 Set 1, расширенные клавиши имеют
  префикс `0xE0` в старшем байте, например `0xE01D` для правого Ctrl. Таблица преобразования из
  `KeyboardEvent.code` находится в `web/src/input/scancodes.ts`.
- `MouseButton`: 0 левая, 1 правая, 2 средняя, 3 назад, 4 вперёд.
- `Wheel`: 120 единиц соответствуют одному шагу колеса. Как в Windows, `dy` больше нуля прокручивает вверх, `dx` больше
  нуля вправо. Клиент меняет знак `deltaY` браузера.
- `Touch`: запись имеет вид `u8 id`, `u8 phase`, `u16 x`, `u16 y`, где `phase`: 0 down, 1 move, 2 up, 3 cancel.
  В одном сообщении максимум 10 записей.
- `Text`: максимум 4096 байт. Используется для экранной клавиатуры Android, ввод выполняется через `KEYEVENTF_UNICODE`.
  Перевод строки и табуляция вводятся клавишами Enter и Tab, `\r\n` даёт один Enter.
- `Special`: 1 Ctrl+Alt+Del (доступно с фазы 6), 2 переключение монитора, если появится несколько мониторов.

### `control`: сервер → клиент

JSON:

```json
{ "t": "hello", "protocol": 1, "display": { "w": 1920, "h": 1080, "hz": 60 }, "codec": "h264",
  "rtp_epoch_ms": 1793872345123.4, "rtp_clock": 90000 }
{ "t": "stats", "adaptive": true, "target_kbps": 32400, "estimate_kbps": 35000, "sent_kbps": 6100,
  "out_kbps": 6400, "loss": 0.0, "rtt_ms": 1.4, "min_kbps": 2000, "max_kbps": 30000, "rate_changes": 12,
  "mode": "game", "active_mode": "game" }
{ "t": "settings", "max_bitrate_kbps": 20000, "mode": "game", "adaptive": true }
{ "t": "pong", "id": 7, "client_ts": 12345.6, "server_ms": 1793872346000.1 }
```

Статистика потока (с фазы 8, D-029):

- `stats` приходит раз в секунду, пока идёт видео. `target_kbps` — цель кодировщика, `estimate_kbps` — оценка
  канала `str0m` или `null`, `sent_kbps` — отдано кодировщиком за последнюю секунду, `out_kbps` — выпущено пейсером
  вместе с повторами, RTCP и заполнением. `loss` — доля потерь из отчётов браузера от 0 до 1, `rtt_ms` — RTT; оба
  `null`, пока отчётов нет. `min_kbps` и `max_kbps` — действующий диапазон цели с учётом режима и предела клиента.
  `mode` — режим, выбранный клиентом, `active_mode` — режим, который идёт сейчас: «Слабая сеть» (`weak`) может
  включиться сама (D-030).
- `settings` — ответ на `settings` клиента: применённые предел в кбит/с и режим, признак адаптивного битрейта.

Часы для замера задержки (с фазы 2):

- `hello` приходит сразу после открытия канала. `rtp_epoch_ms` — Unix-время в миллисекундах, которому соответствует
  RTP-метка 0 видеопотока, `rtp_clock` — частота RTP-меток. Время захвата кадра на сервере равно
  `rtp_epoch_ms + rtp / rtp_clock * 1000` с учётом переполнения 32-битной метки.
- `pong.server_ms` — Unix-время сервера в момент ответа. Клиент берёт обмен с наименьшим временем туда и обратно и
  считает смещение часов: `server_ms − (время клиента при отправке + RTT / 2)`.
- `requestVideoFrameCallback` даёт `rtpTimestamp` показанного кадра. Отсюда «захват→показ» в часах клиента, без
  монитора сервера и без доверия к оценкам браузера.

Бинарное сообщение `0x20` CursorShape:

| Смещение | Тип | Поле |
|---|---|---|
| 0 | `u8` | Тип |
| 1 | `u16` | `shape_id` |
| 3 | `u16` | `hot_x` |
| 5 | `u16` | `hot_y` |
| 7 | `u16` | Ширина |
| 9 | `u16` | Высота |
| 11 | Байты | PNG, общий размер сообщения до 64 КиБ |

Монохромный и маскированный курсор сервер преобразует в RGBA перед сжатием.

### `control`: клиент → сервер

```json
{ "t": "settings", "max_bitrate_kbps": 20000, "mode": "game" }
{ "t": "request-idr" }
{ "t": "ping", "id": 7, "client_ts": 12345.6 }
```

Значения настроек проверяются сервером и ограничиваются допустимым диапазоном. `max_bitrate_kbps` — верхний предел
цели кодировщика, `null` возвращает предел сервера. `mode` — `game` («Игра», 1080p до 30 Мбит/с), `desktop`
(«Рабочий стол», 1080p до 40 Мбит/с) или `weak` («Слабая сеть», 720p до 12 Мбит/с), по умолчанию `game` (D-030).
Поле, которого нет в сообщении, ничего не меняет; неизвестный режим или предел не числом — сообщение отбрасывается.
Предел и режим действуют до конца подключения, клиент повторяет их при каждом открытии `control`. Частота кадров у
всех режимов 60, отдельной настройки нет.

## Файлы

Все пути в API являются относительными к `files.root`, используют `/` и проверяются по правилам из
[SECURITY.md](SECURITY.md).

| Метод и путь | Назначение |
|---|---|
| `GET /api/files/list?path=` | Содержимое папки |
| `GET /api/files/download?path=` | Скачивание, поддержка `Range` |
| `GET /api/files/hash?path=` | SHA-256 файла на сервере, потоковое чтение |
| `POST /api/files/mkdir` | Создание папки |
| `POST /api/files/rename` | Переименование и перемещение |
| `POST /api/files/delete` | Перемещение в `.rcs-trash` |

Запись `list`:

```json
{ "name": "report.pdf", "type": "file", "size": 1024, "modified_at": "2026-11-02T10:00:00Z" }
```

Подробности (D-026):

- Пустой `path` — корень. Ответ `list`: `{ "path": "...", "entries": [...] }`, папки первыми. `type`: `file`,
  `dir` или `link`; ссылки показываются, но не открываются (`403 link`). `.rcs-uploads` в списке нет.
- Тела: `mkdir` — `{ "path" }`, ответ `201`; `rename` — `{ "from", "to" }`, без замены существующего;
  `delete` — `{ "path" }`, ответ `{ "trash": ".rcs-trash/<время UTC>-<hex>/<имя>" }`. Внутри корзины не удаляют
  и в неё не переносят (`403 forbidden`), из неё переносят обратно через `rename`.
- `hash` отвечает `{ "sha256", "size" }`. `download` отдаёт `ETag`, `Last-Modified`, `Accept-Ranges` и
  принимает один диапазон `bytes=` и `If-Range`; при нескольких диапазонах — весь файл.
- Ошибки — `{ "error": "код" }`: `path_*` (`400`, недопустимый путь), `not_found`, `exists`, `not_a_directory`,
  `is_a_directory`, `link`, `path_mismatch`, `forbidden`, `access_denied`, `disk_full` (`507`), `too_large` (`413`),
  `files_unavailable` (`503`, корень не прошёл проверку при запуске).

### Загрузка с докачкой

Размер куска: 8 МиБ. Куски отправляются последовательно, загрузка идёт во временный файл внутри `.rcs-uploads`.

| Метод и путь | Тело | Ответ |
|---|---|---|
| `POST /api/uploads` | `{ "path": "...", "size": 123, "overwrite": false }` | `{ "id": "...", "chunk_size": 8388608, "received": 0 }` |
| `GET /api/uploads/{id}` | Нет | `{ "received": 8388608 }` |
| `PUT /api/uploads/{id}?offset=N` | Данные, заголовок `X-Chunk-SHA256` | `{ "received": 16777216 }` |
| `POST /api/uploads/{id}/complete` | Нет | `{ "path": "...", "sha256": "..." }` |
| `DELETE /api/uploads/{id}` | Нет | `204` |

- Сервер принимает кусок только при `offset == received`.
- Несовпадение `X-Chunk-SHA256` даёт `422`, кусок не записывается.
- Несовпадение `offset` даёт `409` и текущий `received`.
- Клиент после обрыва вызывает `GET /api/uploads/{id}` и продолжает с `received`.
- `complete` проверяет размер, вычисляет SHA-256 всего файла и выполняет атомарное переименование.
- Незавершённые загрузки удаляются через 7 дней.
- `GET /api/uploads/{id}` возвращает также `size`. Кусок может быть короче 8 МиБ, например при продолжении с
  нечётного `received`. При существующем файле и `overwrite: false` создание отвечает `409 exists`.
- Клиент запоминает `id` для пути, размера и времени изменения файла: тот же файл после перезагрузки страницы
  продолжает загрузку.
